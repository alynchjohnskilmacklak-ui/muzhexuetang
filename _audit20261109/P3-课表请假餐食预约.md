## 2. 逐条结论

### 2.1 动作：`parent/schedule` · 周课表读取（小班 + VIP 卡片 + 历史课记录）

- 家长端入口：`src/app/parent/schedule/page.tsx:117-132`（本周课次 `lessons`）、`:134-147`（停课记录 `cancelledLessons`）、`:149-211`（个性化历史 `historyLessons`）；客户端 `parent/schedule/client.tsx:192-199` 按选中孩子二次过滤。
- 写入点：无（纯读）。数据源 `ClassLesson`，关联 `ClassGroup / Teacher / ClassLessonStudent / Attendance / ClassroomFeedback / IntensiveLessonReview`。
- 管理端消费：`(main)/schedule` 同表；教师端消费：`api/teacher/schedule/route.ts:86-122` 同表。
- 越权核查：课次 where 经 `parentVisibleLessonWhere(userId)`（`lib/business-visibility.ts:138-147`）→ 班级 `enrollments.some(parentActiveEnrollmentWhere(userId))`；名册 `lessonStudents.where(student: parentLinkedStudentWhere(userId))`；URL `childId/studentId` 仅用于前端选中态（`resolveParentChildId`，`lib/parent-child-selection.ts:27-33`），数据查询全部按会话解析的归属集合过滤。**安全**。
- 结论 + 证据：
  - `page.tsx:22` `export const dynamic = 'force-dynamic'`；无 SWR、无 `fetch` 课表接口；客户端刷新走 `router.refresh()`（`client.tsx:284` PullToRefresh）。管理员改时间/换老师/停课后，家长下次进入或下拉刷新即直读最新库值，**无快照窗口**。
  - 课次状态过滤：`visibleClassLessonWhere`（`business-visibility.ts:38-42`）`status NOT IN ('CANCELLED','POSTPONED')` + `deletedAt: null` + 班级 `not ARCHIVED` + 课程 `isActive`；本周课次另要求当前 ACTIVE 学期的有效报名（`currentTermEnrollmentWhere`，`schedule/page.tsx:40-54`）。
  - 停课记录单独查询 `status='CANCELLED'`（`page.tsx:137`），带 `cancelReason`；**`POSTPONED` 既不在主课表也不在停课记录区**，家长端看不到延期标识。
  - 历史课记录仅取 `intensiveMode='INTENSIVE'` 且 `attendanceSubmittedAt` 或审核状态非空（`page.tsx:152-161`）；小班历史考勤不在此列。
- 实测（SQL，近 30 天）：SCHEDULED 391、COMPLETED 3、CANCELLED 785（其中 684 已软删）；未软删 CANCELLED 101 行全部挂 ACTIVE 班级；**近 30 天 POSTPONED 0 行**。非 ACTIVE 班级的未取消课次仅 3 行（ARCHIVED，0 行未来课），会被 `visibleClassGroupWhere` 排除。
- 修复方向：① 停课记录区并入 `POSTPONED` 并展示 `postponeFrom`/原因；② 若产品要求家长看到小班历史考勤，历史区需放开 NORMAL 班级口径（当前仅 INTENSIVE）。
- 风险级别：低（POSTPONED 展示缺口为中）。确定性：**[已核实]**。

### 2.2 动作：`parent/leave` · 提交请假申请

- 家长端入口：`parent/leave/client.tsx:91-100` `POST /api/parent/leave`，body `{studentId, lessonId?, reason, leaveDate}`。
- 写入点：`api/parent/leave/route.ts:122-135` 事务内 `LeaveRequest.create`：
  - `studentId`（归属校验后落到 `lessonStudentId || child.id`，`:96`）、`lessonId`（可选，无课次为 `null`）、`reason`、`leaveDate`（本地日区间归一）、`status='pending'`、`replyNote='已提交，等待老师审批'`。
  - 幂等：`pg_advisory_xact_lock` + 同语义键查重，已存在 pending/approved 则复用返回（`:108-121`）。
- 管理端消费：`api/leave-requests/route.ts:36-47`（admin 按学部），页面 `(main)/leave-requests/page.tsx:36`。
- 教师端消费：同接口 teacher 范围 `teacherStudentWhere`（`route.ts:26-30`），页面 `teacher/leave/page.tsx:57`。
- 通知：管理员全员 `:137-155`（href `/leave-requests`）；对应课次教师/班主任 `:157-171`（href `/teacher/leave`）；另有 `ActivityLog` `:173-181`。
- 越权核查：`route.ts:51-54` `findParentChild(await getParentChildren(prisma, userId), requestedStudentId)`，不归属返回 403；`lessonId` 二次校验——课次须在孩子 `recordIds` 报名名册内且科目匹配（`:56-91`，`resolveSubjectLessonStudentIds`），日期不一致 400（`:92-94`）。**安全，无跨孩子提交**。
- 结论 + 证据：**真连通**。家长提交 → 待审单落库 → 管理端/教师端列表立即可见（同表直读，无缓存）。
- 审批回传：`api/leave-requests/[id]/route.ts:49-55` 回写 `status / replyNote / repliedAt / repliedBy`；批准时在事务内把匹配考勤 `PRESENT/LEAVE` 重算为 `LEAVE` 并退/补课时（`:90-168`）；`:175-187` 给家长账号建 `LEAVE_REQUEST` 通知，href `/parent/leave`。家长请假页 SSR 直读 `LeaveRequest`（`parent/leave/page.tsx:67-75`），**非轮询**：重进页面 / 下拉刷新 / 点通知进入即见最新状态与回执。
- 实测（SQL）：
  - 现存 live `LeaveRequest` 仅 **2 行，均 approved**，0 pending、0 rejected；两行 `lessonId=null`，`replyNote/repliedAt` 均已回填。
  - **遗留矛盾（前轮已知，复核成立）**：2 张批准单对应 **12 行考勤仍为 PRESENT**（2026-07-17 4 行、2026-08-03 8 行，同一学生韩霖烁），每行 `hoursDeducted=0.7`；with-lesson 口径 0 行冲突，date-only 口径 12 行冲突。
  - 家长端展示口径判断：请假列表只渲染 `LeaveRequest` 字段（`client.tsx:306-317`），不并列考勤状态；课表历史区仅 INTENSIVE 班级，这 12 行是 NORMAL（`NOT_REQUIRED`）小班课，**不会在家长端同屏出现"已批准 vs 出勤"字样冲突**；但库内口径矛盾真实存在——批准请假却扣了课时，且现行审批路由的考勤重算未回溯这两行（早于重算逻辑入库）。
- 修复方向：对 2 张历史批准单做考勤回溯重算（PRESENT→LEAVE、退还 0.7h/节）；后续若家长端要展示小班考勤，需先消除该矛盾。
- 风险级别：中（历史数据）。确定性：**[已核实]**。

# 第四轮规范：教师端模块传导核查（_SPEC4）

## 0. 与上一轮的关系
沿用 `_SPEC3.md` 的**四档判定**与**每条结论的固定结构**，只把主体从"管理端"换成"教师端"：

> **老师在教师端点了一个控件 → 数据写进去 → 管理端 / 家长端有没有真的跟着变；反向：管理端的配置改动，教师端有没有真的读到最新值。**

四档定义（同 SPEC3，必须只用这四档）：

| 档 | 定义 |
|---|------|
| **真连通** | 教师端写入 → 管理端/家长端读**同一表同一字段**，且有实测数值一致 |
| **部分连通** | 有读方，但读快照/缓存/另一口径，或要手动触发才同步，或只覆盖部分记录 |
| **孤岛** | 写进去了，但全仓**没有任何管理端/家长端读点** |
| **假控件** | 有按钮但①接口不存在 ②字段被白名单丢弃 ③被 `.catch(()=>{})` 吞 ④只改前端 state |

## 2. 硬性要求

1. **控件级枚举**：同一页面的"保存草稿"和"发布"是两个动作；批量操作、拖拽、Tab 切换后的提交都要单列。
2. **页面覆盖要完整**：分给你的页面，每页都必须有结论（有能力就列动作，纯展示页就写"纯展示，无写动作，证据 GET 端点行号"）。
3. **孤儿页**：以 `src/components/Layout/TeacherLayout.tsx` 的导航数组为权威（桌面 `:60-80` 附近、移动 `:185-195` 附近）——凡是 `src/app/teacher/**/page.tsx` 存在但不在这两个数组里、也不被其它页面链式跳转到的，判"无入口孤儿页"，要写清"能否通过 URL 直达、页内是否有写动作"。
4. **反查两端消费点必须靠 grep**（限定 `src/app/(main)/**`、`src/app/api/admin/**`、`src/app/parent/**`、`src/app/api/parent/**`、`src/lib/**`），不能凭页面名字猜。
5. **重点盯这几组**（全局都相关，按你的模块取用）：
   - 考勤提交 → `TeacherSalaryTransaction` 与 `HourTransaction` 是否真的产生流水；点名（`ClassroomPick`）是否仍然**不碰账务**（单向设计是否还成立）
   - 课堂反馈发布 → 家长端可见性与已读状态；草稿是否泄漏给家长
   - 反馈图片 → 家长侧鉴权、原上传教师撤销后是否仍可看
   - 掌握度 → 是否真写 `MasteryRecord`（路由现已存在，需确认写入成功而非 404）
   - 教师端薪资页显示值 vs `TeacherSalaryConfig` 实际配置值（写死的默认值就是孤岛）
   - 名单为空（实测 592 节中 160 节 27.0% 名单空）对点名/考勤的影响
6. **只读**：只允许 `SELECT`；脚本放 `_audit20261109\`，`NODE_PATH` 指向仓库 `node_modules`；**不碰 3000 端口 dev、不改源码、不 migrate、不重启**。
7. **基线纪律**：所有结论必须基于**当前源码**重新取证，**不得直接引用 11-08 的旧结论**。若发现某条旧结论已失效，写进你自己的"基线与前轮差异"小节。

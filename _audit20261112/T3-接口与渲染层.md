## 1.2 逐接口详析

### 1.2-1 `GET /api/feedback`（反馈列表，家长/教师共用）

**文件**：`src/app/api/feedback/route.ts`

- **查询形态**
  - `findMany`：`route.ts:112`；`include`：`teacher`（select 受限）→ `classLesson` → `group.course`（`route.ts:114-117`），三层嵌套。
  - 已读回执：家长身份先查一次本人已读范围（`route.ts:81-87`）；列表取出后按 `feedbackIds` 批量二次查回执（`route.ts:152-157`），**不是循环 N+1**；内存逐行 map（`route.ts:158-163`）。学生名单同理批量查（`route.ts:126-128`）。
  - **字段裁剪缺失**：反馈本体未写 `select`，整行返回，含：
    - 长文本：`lessonContent`（`@db.Text`，schema `:925`）、`overallComment`（`:936`）、`summary`（`:934`）、`parentReply`/`adminReply`；
    - JSON 字段：`homework`、`studentRatings`、`knowledgeCard`（schema `:937-939`）；
    - 图片：`imageUrls` 数组（本地 5,220 槽位 / 3,065 行带图）。
  - 图片变体：`resolveFeedbackImageVariants`（`lib/file-asset-variants.ts:35-59`）一次 `$queryRaw` 批量解析，未形成 N+1。
- **返回规模**：`take: limit`，`limit = Math.min(200, sp.get('limit') || 50)`（`route.ts:55,119`）；**当前无 offset/游标参数**。按本地实测行体积推算：200 行完整 JSON 约 **300–600 KB 原始**，gzip 后约 90–180 KB（估算，未 build 验证）。
- **缓存可行性**：含家长已读状态、回复内容、个人孩子数据 → **必须 no-store**；但列表卡片所需字段与详情字段可拆分（见改法）。
- **改造建议**
  1. **字段裁剪**（列表 `select` 清单）：`id, studentId, studentNameSnapshot, displayStudentName, status, notifySent, parentReadAt, parentRepliedAt, adminReply, sessionDate, createdAt, subject, tags, imageUrls, imageCount, lessonContent(截断 80 字), summary, overallComment(截断), homework(仅标题数组), studentRatings(仅总分), knowledgePoints`；长正文/完整 JSON 留给 `/api/feedback/[id]` 详情接口。
  2. **游标分页**：现仅有 `limit` 入参（`route.ts:55`），无 offset；建议新增 `cursor`（按 `createdAt desc, id desc`），前端接入点：家长端 `src/app/parent/class-feedback/client.tsx`（列表渲染区）；管理端 `src/app/(main)/classroom-feedback/page.tsx:372,384`（SWR `limit=200` 拉取区）。
  3. **观测点**：`[db-performance]` 中 `model=ClassroomFeedback, operation=findMany`；现有日志不带行数/字段，建议在中间件补 `args.select ? 'projection' : 'full'` 标记（见⑥，需改代码，本轮仅记录）。

### 1.2-2 `GET /api/admin/classroom-feedback`（管理端反馈 + 当日课表）

**文件**：`src/app/api/admin/classroom-feedback/route.ts`

- **查询形态**
  - 反馈列表：`route.ts:55-79`，include teacher / classLesson.group.course；`take: limit`（100/200）。
  - **当日课表二次全量查询**：`route.ts:81-110`，无 `take`，嵌套 `enrollments.student`、`classroomFeedbacks(id,status)`、`attendances(studentId,status)`、`lessonStudents`。当日课表数量受 ClassLesson 总量约束（本地 3,686），学期内单日通常数十节，但嵌套关系会放大行数。
  - 反馈行在 `route.ts` 后段 map 时才切片字段（`lessonContent/overallComment` 截断），**DB 层仍取整行 JSON**。
- **返回规模**：反馈 100–200 行 + 当日课表全量嵌套；本地数据量小，生产课表/出勤增多后二次查询是主要放大点。
- **缓存可行性**：管理端视图，含反馈状态与教学数据 → no-store；当日课表部分可与反馈列表拆分到独立接口，便于分别缓存/懒加载。
- **改造建议**
  1. 反馈列表补 `select`（同 1.2-1 清单，管理端可多取 `teacherId/feedbackGroupId`）。
  2. 当日课表查询只取排班矩阵需要的列：`id, lessonDate, startTime, endTime, status, groupId, teacherId, group{ room{name}, course{name,subject} }, enrollments{ studentId }`；去掉 `classroomFeedbacks/lessonStudents` 嵌套计数，改 `_count` 或独立轻量接口。
  3. 前端接入点：`src/app/(main)/classroom-feedback/page.tsx`（整页 1,596 行，反馈表格与抽屉分区见②）。

### 1.2-3 `GET /api/dashboard`（管理端首页统计）

**文件**：`src/app/api/dashboard/route.ts`

- **查询形态**
  - 首轮 21 路 `Promise.all`：`route.ts:87-109`。多数为 `count`/受限 `select`，形态尚可。
  - `parentMessages`：`route.ts:203-216`，**无 take**，嵌套 `replies`（role/createdAt/已读标记）；本地仅 39 行，生产家长沟通增多后是增长点。
  - `studentCreatedAtRows`：`route.ts:335-338`，全量活跃学生只取 `createdAt`，拉回 JS 在 `route.ts:386` 循环按月分桶 → **应改 SQL `groupBy`**。
  - `sixMonthClassLessons`：`route.ts:339-345`，六个月课表全量拉到 JS 做月度分布 → **应改 `groupBy` 月份聚合**。
  - `upcomingRows`：`route.ts:467`，`take: 300`，有上限。
- **返回规模**：聚合结果为主，单包不大；重在读库行数与 JS 聚合成本。
- **缓存可行性**：管理端聚合看板，数据分钟级新鲜度可接受 → 可对**无个人身份维度**的汇总指标（课时分布、新增学生月度、课表排期）加 `private, max-age=30, stale-while-revalidate=60`；含未读消息数/待办的接口必须 no-store。注意全局 `/api/*` no-store 会被路由内 `headers` 覆盖（已有先例：`/api/courses`，`src/app/api/courses/route.ts:22-24`）。
- **改造建议**
  1. `studentCreatedAtRows` → `prisma.student.groupBy({ by: [month('createdAt')], _count: true })`；`sixMonthClassLessons` → `groupBy` 月份 + `_count`/课时求和。
  2. `parentMessages` 列表若仅用于未读数，改 `count({ where: { isReadByParent: false } })`，不要拉 replies。
  3. 观测点：`[db-performance]` 的 `Student.findMany`、`ClassLesson.findMany`、`ParentMessage.findMany`。

### 1.2-4 `GET /api/teacher/dashboard`（教师工作台）

**文件**：`src/app/api/teacher/dashboard/route.ts`（薄封装）+ `src/lib/teacher-dashboard.ts`

- **查询形态**
  - 路由层：`route.ts:11-13`，并行取看板数据 + 消息未读 + 通知未读。
  - 学生卡片：`teacher-dashboard.ts:114-152`，嵌套 `enrollments`、`attendances(take 3)`、`performancePosts(take 1)`、`examPapers(take 3, 含 questions.mastery)`；子关系有 take，形态可控，但每个学生都触发嵌套关系查询（Prisma 按关系批量，非逐行 N+1）。

| 分类 | 接口类型 | 建议 Cache-Control | 依据 |

- **观测点**：图片请求字节数、`/_next/image` 响应耗时、优化失败回源原图比例。

## 3.4 数据库与连接池

- **连接池**：`lib/prisma.ts:11-14`，URL 缺参时注入 `connection_limit=30&pool_timeout=30&connect_timeout=10`；**双学部双客户端**（JUNIOR/SENIOR，`:69-85`），理论上限 **2 × 30 = 60** 连接。compose 中 Postgres 15 `mem_limit: 512m`、`shm_size: 128m`（`compose.production.yaml:33-34`），未显式设 `max_connections`（默认 100）；60 连接上限距默认上限有余量，但需结合生产实际并发复核。
- **慢查询日志**
  - Prisma 客户端日志：开发 `warn,error`，生产仅 `error`（`prisma.ts:18`）；**未开启查询级别 slow log**。
  - 业务中间件 `$use`（`prisma.ts:21-42`）：失败必记；成功 **≥500ms** 记录；其余 **1% 采样**；输出 `[db-performance] {model, operation, durationMs, outcome, at}`——**不含 SQL 文本、参数、返回行数、连接等待时间**（代码注释明确不记 SQL/值/错误）。
  - Postgres 侧 compose 未配置 `log_min_duration_statement`。
- **既有日志观测**：`dev-server-old.log` 389 条中最慢为 `queryRaw 692ms`（Vocab 目录类全量查询嫌疑），其余 `findMany/count` 多在 26–76ms（本地开发库，不代表生产）。
- **Redis**：compose 起 Redis 7-alpine（128MB，`compose.production.yaml:4-16`），`RATE_LIMIT_DRIVER=redis`（`:56`）；**仅用于限流**，未作为接口/查询缓存层。
- **建议**（记录，不改）
  1. 生产库开启 `log_min_duration_statement`（如 200ms）或在 Prisma 中间件补行数/耗时分布；复核双客户端连接数与 PG `max_connections`。
  2. 1.2 节中标注的全量拉取/JS 聚合查询，优先用 `groupBy` 下推，降低扫描行数。

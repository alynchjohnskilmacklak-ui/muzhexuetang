## 3. 接口载荷逐条评估

> 估算口径：本地 dev 库样本长度 × 字段数；响应体为 JSON，`next.config.ts` 已开 `compress: true`（gzip/br）。未发真实请求，KB 为区间估算。

### 3.1 `GET /api/parent/vocab/deck`（`api/parent/vocab/deck/route.ts`）

- **是否全量**：服务端先 `loadVocabEntries(prisma)`（:56）把 **2,973 条全量从 DB 读出**，在 JS 内按册/单元/进度过滤（:64 起 `progressRows`），最后 `shuffledPool.slice(0, limit)`（:79）。`limit` 解析见 :37-38：传正整数则 `min(limit, 50)`，**不传/非法时 `limit=0` → 不切片、回传整个池**；前端 `page.tsx:141` 固定传 `limit=16`。**传输层切片依赖调用方传参，DB 查询层未下推过滤/分页**。
- **返回结构**：`VocabQuestion[]`，每题含 `wordId/headword/phonetic/pos/note/meanings/prompt/options[4]/answerIndex`，命中时挂 `expansion`（拓展：考点/语法/搭配/易错点/例句/应用/来源）。
- **大字段**：`expansion` 是最重字段（拓展库 2.56 MB / 2,774 条，单条平均约 950 字符）；未命中拓展的题只带词条本体（DB 行均 150 字符）。
- **单次响应估算**：16 题 ×（本体约 0.3–0.5 KB + 命中拓展约 1.0–1.8 KB）≈ **5–30 KB JSON**，gzip 后约 2–10 KB。
- **现状分页参数**：`limit`（:37-39, :79；前端传 16，上限 50，缺省全量池）；无 `cursor/skip`；过滤条件 `grade/volume/unit` 在内存完成。

### 3.2 `GET /api/parent/vocab`（`api/parent/vocab/route.ts`）

- **是否全量**：同样先 `loadVocabEntries(prisma)`（:49）全量读 2,973 条，在内存聚合 `units`（册/单元/小节/统计）；`progressRows`（:70）按学员查 `VocabProgress`；`recentSessions` 已 `take: 10`（:104）。
- **返回结构**：`units[]`（目录元数据 + 每单元 `count/sections/stats`）、`progress`（按 `wordId` 键控的状态字典）、`stats`、`availableBooks`、`recentSessions[10]`。**不回传词条本体（headword/释义列表）**。
- **大字段**：`progress` 字典随已学词数增长；dev 库仅 32 行。
- **单次响应估算**：目录 + 进度字典 ≈ **4–12 KB JSON**；风险点是词条全量读入内存做聚合，词量翻倍后 DB 读与内存压力上升，响应体本身不大。
- **现状分页**：无；目录型接口，单元数固定，通常不需要分页。

### 3.3 `GET /api/parent/practice-results`（`api/parent/practice-results/route.ts`）

- **是否全量**：
  - `practiceResult.findMany`（:129，`orderBy finishedAt desc`）**无 `take/skip/cursor`**，把该学员全部 `PracticeResult` 读成 `resultMap`（含 `answers`、`wrongIds`）；
  - `practiceAttempt.findMany`（:133）**已分页**：`skip=(page-1)*pageSize`、`take=pageSize+1`（:136-137，`pageSize` 30，`nextPage` 回传）。
- **大字段**：`PracticeAttempt.questionSnapshot`（平均 693.5 字符、最大 1572）与 `answers`（平均 116.5）随每条记录回传；`PracticeResult.answers` 平均 96.7 字符。
- **单次响应估算**：历史页 30 条 ×（快照约 0.7–1.0 KB + answers）≈ **25–35 KB/页**；`resultMap` 为全量字典，dev 库 12 行体量小，生产随练习次数线性增长。
- **现状分页参数**：`page/pageSize`（attempts 已接）；`resultMap` 未分页。
- **server bundle 牵连**：路由顶部静态 import `PUBLISHED_PRACTICE_SETS`（:6）与 `ALL_PRACTICE_SETS`（:7），仅用于标题映射与判分，把 6.43 MB 题库聚合进该 server 链路。

### 3.4 `GET /api/attendance/today`（任务清单写作 `teacher/attendance/today`，实际路径为 `api/attendance/today/route.ts`）

- **是否全量**：按当日 `lessonDate` 区间查 `classLesson.findMany`（:64），**时间范围天然有界（单日）**，无显式 `take`；按角色收窄：teacher 限本人课、parent 限子女关联课、admin/teacherId 全量。

## 4. 重复与权威源：DB vs 静态 JSON

### 4.1 词库：DB 与静态 `vocab-sets` **1:1 重复**

| 口径 | 词条数 | 分册 |
|---|---:|---|
| DB `VocabWord` | **2,973** | 七上 629 / 七下 461 / 八上 549 / 八下 603 / 九上 484 / 九下 247 |
| 静态 `VOCAB_BANKS`（`vocab-sets/` 12 文件） | **2,973** | 与 DB 分册对齐（导入脚本 `scripts/import-grade7a/7b/8a/8b/9a/9b-vocab.ts` 逐册写入） |

- **权威源 = DB**：运行时读路径全部走 DB——`lib/vocab-catalog.ts` 的 `loadVocabEntries(prisma)` 被 `deck`/`vocab`/`session` 三个路由调用；静态 `VOCAB_BANKS` 经 `lib/vocab-bank.ts:1` 进入 server bundle，但生产调用方传入的都是 DB entries，静态数组仅作纯函数默认值与单测夹具。
- **静态一份的作用**：① 历史导入源（`scripts/import-*-vocab.ts` 把静态词条灌进 DB）；② `vocab-sets/*.test.ts` 与 `vocab-bank.test.ts` 的回归夹具；③ 离线改词底稿。
- **拓展库 `vocab-expansions`（2,774 条）不与 DB 重复**：它是按 `wordId` 键控的可选富集（考点/搭配/例句等），DB `VocabWord` 表内无对应列；目前只在 `deck` 路由按题挂载。

### 4.2 题库：静态 JSON 即生产数据源，DB 只存作答记录

- 题目本体（10,568 题 / 1,399 组）**只存在于 `src/data/` 静态 TS**；DB 侧只有 `PracticeResult` / `PracticeAttempt`（作答、快照、统计），没有题库表。
- 因此题库**不存在"DB 与静态双份重复"**；静态文件既是源也是 server bundle 内容。

### 4.3 "只留一份权威 + 另一份归档"可行性（不删，只归档）

- **词表静态 12 文件（214.5 KB）**：运行时已不依赖 `VOCAB_BANKS` 数据本体，可在确认三条路由不使用默认导出后，把静态词条迁出运行时目录（如 `archive/vocab-source/` 或保留为 `scripts/seed/` 数据源），server bundle 不再打包；`scripts/import-*-vocab.ts` 与测试引用同步改路径。**风险**：需先确认 `allVocab()`/`filterVocab()` 无生产无参调用（本轮 grep：生产调用均显式传 DB entries）。
- **拓展库 2.56 MB**：当前是 server 运行时依赖，**不能归档**；只能改懒加载（见 §5.2）。
- **题库静态 TS**：生产数据源，不可归档；只能按科目/册次拆分懒加载。

## 5. 分层改法（收益 / 成本 / 风险 / 验证）

### 5.1 客户端：`/parent/vocab` 三册数据按需加载

- **改法**：`page.tsx:13-15` 的 `VerbMasteryHub`/`GrammarHub`/`CompositionHub` 改为 `next/dynamic`（`ssr:false`）或 stage 门控 `import()`；`EnglishHub`（:19-21 同时引三份）在首屏 `VocabHome` 阶段不挂载，三份 english 数据随之延迟。
- **收益**：初始 client chunk 静态数据从 97.8 KB 源码降到接近 0（仅保留 Hub 壳代码）；延迟 chunk 在进入对应 stage 时才拉取。
- **成本**：低–中；需处理 stage 切换时的加载态与 `EnglishHub` 对三册的聚合引用。
- **风险**：低；内容不删，只是分包。注意 antd 组件与 Hub 壳的共享 chunk 不要被重复打。
- **接入点**：`parent/vocab/page.tsx:8-15`；子组件 `_components/{VerbMasteryHub,GrammarHub,CompositionHub,EnglishHub}.tsx`。

### 5.2 服务端：大静态 JSON/TS 懒读，移出启动 bundle

1. **`obsidian-question-bank` 三份已接线 JSON（1.20 MB）+ `language.json`（746 KB）→ 运行时 `fs.readFile + JSON.parse`**
   - 可行性：Next server 运行时可访问仓库内 JSON；把顶部 `import x from '....json'` 改为按科目/册次在请求处理函数内 `await fs.readFile(path, 'utf8')` + `JSON.parse`（加内存缓存），JSON 即不进 server bundle。
   - 收益：server bundle 减少约 1.93 MB（含未接线的 `language.json` 若一并迁移）；冷启动内存与构建体积下降。
   - 成本：中；需补路径解析（`process.cwd()` / `path.join`）、解析失败容错与缓存失效策略。
   - 风险：中；SSR/容器化部署时 JSON 必须随产物拷贝（确认 `output: standalone` 是否复制该目录）；`fs` 不能进 edge runtime，确认这些路由均为 Node runtime。
2. **`practice-sets/` 69 文件 / 6.43 MB → 按科目运行时动态 `import()`**
   - 可行性：server 路由处理函数内 `await import('@/data/practice-sets/math-questions')` 按选中科目/册次加载；Next server 支持动态 `import()` 并生成独立 server chunk。
   - 收益：首屏/冷启动不再一次性解析 6.43 MB；单科目 chunk 按需加载。
   - 成本：中–高；`parent-practice-bank.ts` 的合并/目录统计逻辑目前依赖全量聚合，需先把"目录元数据"与"题目本体"拆开（目录轻量、题目懒加载），否则统计仍要全量读。
   - 风险：高；`published/parent/all` 三套聚合与判分修订映射耦合，改动需配合 §5.6 全量条目校验。
3. **知识库 `knowledge-references-published-bank-2026.json`（1.95 MB）→ 同上 `fs` 懒读**
   - 仅 `api/teacher/ai-feedback/chat/route.ts` 一条 server 链路使用，改造面小，收益明显。
4. **`vocab-expansions` 2.56 MB → 按 `wordId` 分片懒读**
   - 现状 `index.ts` 静态聚合 52 份；可改为按册/单元分片动态 `import()` 或 `fs` 懒读 + LRU 缓存，`deck` 路由只取当前题组命中的分片。

> 附注：`next.config.ts` 的 `optimizePackageImports` 只作用于 `antd/@ant-design/icons/lodash-es/date-fns` 这类 node_modules 包，**管不到自有 `src/data`**；自有数据必须靠拆分/懒加载/`fs` 外置解决。

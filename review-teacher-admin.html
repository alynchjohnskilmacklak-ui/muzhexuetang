一、审查范围与方法

范围
  • 教师端 src/app/teacher（25 个路由）与管理端 src/app/(main)（41 个路由）全部页面 + 对应 client 组件 + API 调用点

「导航不可达」判定标准：全代码库检索该路由的 href / router.push 引用，仅 API 路由或 robots 等非 UI 引用视为不可达。

三、P1 · 相似功能合并建议（减少导航）

① 管理端 · 沟通类三页合一 → 「沟通中心」

现状路由功能规模
/parent-messages家长留言监控 + 管理员回复（/api/messages）23,593 B
/notifications消息通知：编写 / 群发 / 失败重试（/api/notifications）19,121 B
/communications（孤儿）家校沟通流（/api/parent-communications）9,811 B

合并方案：1 个导航项「沟通中心」，页内 3 Tab：家长留言 / 通知发送 / 家校公告。
理由：三者都是「运营 → 家长」的沟通动作，数据流同源（教师留言、家长互动数据两端共用），管理动作高频切换。

② 管理端 · 反馈与表现两页合一 → 「反馈与表现」

现状路由功能规模

/performance（孤儿）在校表现：情绪动态 / 徽章 / 家长沟通9,812 B + 详情

合并方案：1 个导航项「反馈与表现」，页内 2 Tab：课堂反馈 / 表现动态。
理由：两者同属「学生成长记录」数据域（教师端 /teacher/feedback 一个入口已同时管理二者；家长端档案「时间线」也把反馈与动态合并展示）。管理端拆成两个入口属重复导航。

四、P2 · 功能与 UI 完整性核查

功能合理性

  • ✅ 收费管理（/fees）明确「纯管理端手动收费台账，不推送家长」——与家长端缴费查看职责分离，设计正确
  • ✅ 家长便捷登录（/parent-access）一次性激活入口——符合实际运营场景
  • ✅ 管理端 dashboard 的「三步开始管理工作」引导、教师端 dashboard 的「查看今天的课 / 提交考勤 / 发布反馈」引导——符合角色实际
  • ✅ 中考志愿模块按 division 过滤：高中部不显示志愿组（MainLayout isSenior 逻辑）——符合业务
  • ⚠️ 家长端也挂载了志愿相关路由（/parent/volunteer、/parent/volunteer/schools 11,666 B）——数据与管理端共用，合理；但建议核对家长端导航是否给初中家长开放了入口
  • ⚠️ 教师端「业务总览」服务目录页与家长端/官网服务介绍内容同源——教师角色价值存疑（见 P1-⑤）

UI 完整性

  • ✅ 三端布局体系完整：TeacherLayout / MainLayout / ParentLayout + MobileLayout 响应式（教师 tabs、管理端 drawer、家长端 tabs）
  • ✅ 角色配色统一：--color-role-teacher/admin/parent 设计令牌，侧栏/强调色一致
  • ✅ 页面多为「薄 page + client 组件」结构，功能均落实在 client 中（早期扫描误判的空壳实际都有实现）
  • ⚠️ 超大单页文件（webpack 打包影响首屏，与「网站反应慢」相关）： /volunteer-sim/rank-query 212 KB、/teacher/feedback 92 KB、/courses 89 KB、/schedule 目录 97 KB —— 建议对 60 KB 以上页面用 next/dynamic 拆分或组件化
  • ⚠️ 教师端 / 管理端均有 1-2 处导航项指向薄页（/teacher/study-hall、/teacher/messages 等 page 仅 400 B 左右转发），结构正常但需确认对应 client 已加载完成

六、结论与建议优先级

  • 第一步（低成本高价值）：为 4 个孤儿页补导航入口 —— 尤其是 /grades 试卷管理（重要功能当前完全不可用）、/volunteer/quota 名额表。纯导航配置改动，零业务风险。
  • 第二步（中成本）：沟通中心三合一、中考志愿四合一 —— 页面内部 Tab 化重组，API 不变，数据零迁移。
  • 第三步（按需）：反馈与表现合并、教师档案+日志合并、教师端福利薪资/课表合并 —— 涉及页面合并与导航调整，工作量中等。
  • 性能顺带项：60 KB+ 大页面按需拆分（next/dynamic），缓解整体加载慢。

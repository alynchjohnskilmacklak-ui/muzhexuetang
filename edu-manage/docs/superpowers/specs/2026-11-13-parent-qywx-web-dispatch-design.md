# 家长企微通知网页即时处理设计

## 意图

管理端提交家长通知后，网页立即创建对应的企微待确认任务，不再依赖服务器定时任务或 VNC 操作。员工仍需在企业微信确认发送。

## 背景与目标

当前 `POST /api/notifications` 只将通知写入本地队列，`/api/cron/retry-notifications` 才会调用企微。生产 root crontab 为空，记录因此停留在“等待创建企微任务”。目标是让管理端提交后能立即得到企微创建结果，并能从网页处理已有队列记录。

## 方案比较与选择

1. **保留队列，配置服务器定时任务**：保留现有后台模式，但需要可靠维护服务器 cron，网页提交后仍不能即时确认结果。
2. **管理端网页即时处理（选择）**：批量保存所选学员通知后，由网页调用受权限保护的后台处理接口；后台按家长归并通知、创建企微任务并立即回写状态。通知记录页为已有排队项目提供“立即创建企微任务”操作。
3. **网页直接向家长送达**：当前企业微信客户群发 API 只创建待发送任务，要求员工在企业微信确认后才发送，不能通过本系统绕过这一步，因此不作为实现目标。

## 约束与行为

- 每个家长每天最多创建一个企微群发任务；同一家庭的多条通知合并为一份家校简报，孩子与家长关联规则保持现状。
- 网页只有在企微返回任务编号并成功保存后，才显示“待企微确认”；仍在队列、处理失败和已创建待确认要分别显示，并保留失败原因。
- 新提交的一批通知在批次创建完成后统一触发处理，避免同一家长因逐条提交而漏进简报。
- 旧的 `queued` 记录可从通知记录页发起即时处理；已有 `pending_confirm` 任务不能重复创建。
- 企微最终发送继续由员工在企业微信确认。本次不安装服务器 cron，不改变自动通知来源的既有队列策略，也不调整通知文案或数据库结构。

## 验收标准

- 管理端提交通知后，结果明确区分“已创建企微待确认任务”和“创建失败”，不再把本地排队误报为企微待确认。
- 现有排队记录可从网页处理，并能在企微对应发送成员的待确认列表中核对。
- 单家长每日限额、联系人/发送成员绑定和家庭简报隐私边界继续生效。
- 企微创建任务后不自动发送，仍等待员工手动确认。

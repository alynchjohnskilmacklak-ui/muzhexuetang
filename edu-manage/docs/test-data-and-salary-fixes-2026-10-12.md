# 演示数据泄漏与薪资结算修复

## 截图中的演示数据来源

图一、图二的内容直接对应源码中的演示回退，不是从这两张截图就能认定为数据库污染。

- 首页把空的教师履约、今日课表、教师约课列表替换为 `MOCK_COMPLIANCE`、`MOCK_SCHEDULES`、`MOCK_APPOINTMENTS`。
- 课程管理把空的个性化课程列表替换为王祁涵、田昊彬、马紫晨等演示卡片，统计数字也来自演示常量。
- 课堂闭环接口在没有实际课程/留言时返回假课次、假留言；教师履约接口接受虚构教师 ID 并返回样例。
- 班级、约课详情接口原来只查演示字典，没有读取实际课次，也没有管理权限校验。

以上回退全部移除，空列表不再冒充真实业务。课程统计改为读取数据库中的有效报名、实际课次和完成情况；详情接口改为读取真实课次，并检查管理身份、学部、批次和删除状态。

未按学生姓名批量删除数据库。马紫晨等姓名也可能对应真实学员，不能作为清理条件。若正式库中另外存在测试种子记录，需先确认精确 ID 和关联数据，再走回收站；本轮没有执行正式库清理。

## 薪资问题与修复

原先存在三种不一致：管理端遍历结算记录时会被更旧的时间覆盖；两端余额按时间截断，但实际结算按 `settledAt` 选择流水；结算候选在事务外读取，重复或并发确认可能处理同一批流水。净额为零但仍有待结算流水的情况也无法结清。

现在统一规则：

1. 新流水按明确的结算时间和批次判断待结算状态；旧的无批次结算凭证保留日期截断兼容，且按教师取最新凭证，不依赖排序。
2. 候选读取、领取流水、写入结算凭证与审计日志在一个可串行化事务中完成，序列化冲突可重试。
3. 领取时再次要求流水未结算，数量不匹配就拒绝提交。已结清记录不会重复生成凭证。
4. 确认窗口展示教师、范围、笔数和金额；接口检查批次及确认金额变化，变化后要求重新核对。
5. 零净额但非空的流水可以结清；负数余额可登记账目结清，界面明确说明不代表实际付款。未删除或改写负数管理调整来伪造归零。
6. 同一教师所选范围的课时、反馈、调整、小班和个性化课程待结算余额一起归零；其他教师不受影响。所有教师结清后，待结算总和才为零。
7. 结算后的新流水仍会计入新的待结算余额，不能因时间早于新结算凭证就被忽略。
8. 两端刷新待结算余额并显示读取失败/重试；确认窗口增加手机宽度、居中和加载保护。网络异常或金额变化时有明确提示。
9. 薪资月份按上海时区计算，两端、结算和导出的周期起点共用规则。

## 数据留存与导出

没有删除原始应发流水。数据库保存每条流水的 `settledAt`、`settlementBatchId`，保存结算凭证，审计日志保存本次源流水 ID、笔数、金额与时间范围。

Excel 保留历史总额与全部明细，另列待结算金额和已结算应发金额。明细增加结算状态、结算时间、批次 ID，结算记录表也包含批次 ID。

## 补充：确认结算后弹窗一直保留

根据后续描述，问题发生在确认提交阶段，不是打开弹窗阶段。原来只有短暂的失败提示，没有弹窗内错误详情，且请求缺少超时保护，容易表现为没有反应。

- 提交期间，窗口内显示处理状态，确认按钮显示「正在结算」。
- 接口明确失败时，在弹窗内保留具体错误；不会失败后关闭并假装成功。
- 有效成功凭证返回后，立即关闭确认窗口，再刷新余额；刷新失败不会被误报成结算失败。
- 请求超过30秒、网络中断或返回无效成功内容时，说明结果尚未确认，禁用当前窗口的重复确认，要求先刷新余额/流水核对。
- 对缺失数据库结构、连接池繁忙、并发冲突等服务端情况返回可读提示。
- 新增5项客户端提交测试；全套测试更新为142个文件、642项通过。正式服务器具体失败原因尚未通过线上日志或真实点击确认。

# 数据管理与系统设置专项代码审查

日期：2026-10-12。只读审查；没有修改业务代码、系统配置或数据库，没有执行备份、恢复、删除、清理或重置。

## 结论

主要问题不是模块数量本身，而是同一业务存在两套操作入口、不同删除恢复规则，以及“设置保存成功”不等于“业务实际应用”。目前数据管理像第二套业务后台，系统设置又混入了账号、权益文案、导出和永久清理，使用边界不清晰。

优先顺序：统一删除恢复 → 阻止无业务副作用的底层直接修改 → 修保存失败却提示成功 → 明确备份与导出 → 接通配置消费者 → 整理模块。

## 范围和验证

- 对数据管理14个入口、系统设置13个入口，核对页面组件、调用接口、配置模型与相关消费者。
- 重点追踪通用实体编辑/删除/恢复/批量操作、课时调整、数据健康、备份恢复、数据清理、账号绑定与设置开关。
- 专项已有测试：数据管理列表接口与学部分域测试共2个文件、6项通过。它们没有覆盖全部写入、恢复或系统设置开关。
- 本报告依据代码，不是浏览器逐按钮验收；没有实际制造业务数据或故障。浏览器工具上一轮被安全策略阻止，本轮没有绕过策略。
- “未接通”指本次搜索的 `src` 和 `scripts` 范围未找到配置读取或执行路径，不等于已证明所有外部服务都没有消费者。

## 一、优先问题与代码依据

### P1：单条删除、批量删除、恢复是三套不同规则

`src/app/api/admin/data-admin/[entity]/[id]/route.ts` 的 DELETE 对学员、班级、课次、试卷、资料调用 `softDeleteEntity`；批量接口 `src/app/api/admin/data-admin/[entity]/batch/route.ts` 却直接 updateMany 修改状态，没有调用同样的关联处理。

`src/lib/data-admin/entities.ts:181` 把 INACTIVE、ARCHIVED、CANCELLED 当成删除状态；这些本身又是正常业务状态。结果是“离校、归档、取消”和“已删除”混在一起，批量删除也可能没有相应回收站记录和关联清理。

更严重的是单条 PATCH restore 和批量 restore 都主要恢复状态；没有对 Student、ClassGroup、ClassLesson 等清除 deletedAt、处理删除批次及关联记录。业务可见条件同时要求 deletedAt=null，例如 `src/lib/business-visibility.ts:3`。因此可能“数据管理恢复成功，但家长端仍看不到”。

建议：删除/恢复共用现有回收站服务，批量操作只是逐条调用同一业务规则；删除与停用/归档/取消分别命名。恢复前预览受影响对象和冲突，结果显示成功、失败及原因。

### P1：通用编辑把所有字段当字符串

`src/app/(main)/data-admin/client.tsx:1219–1224` 遍历全部 editableFields，用同一个 Input 和 String(value) 显示，用户编辑后写入 e.target.value。服务端 `src/lib/data-admin/entities.ts:171` 只过滤字段名，不转换或校验类型。

受影响的具体字段包括毕业年份、班级人数、课次时长、布尔值、知识点数组和作业JSON。未编辑的字段可能还保留原类型，但一旦编辑就会变成字符串；错误多表现为 Prisma 校验失败和“更新失败”，无法告诉用户哪个字段有问题。字段标题还是英文数据库名，关联ID没有选择器。

建议：普通业务内容使用对应业务表单；必须保留的修正项用字段schema定义中文名称、类型、单位、范围、选项与权限，前后端共同校验。不能把所有实体变成万能文本编辑器。

### P1：直接修改考勤、课次、反馈绕过业务闭环

`src/lib/data-admin/entities.ts:61–81` 允许直接编辑课次日期、时间、老师，考勤状态、actualMinutes、hoursDeducted。`[entity]/[id]/route.ts` 普通 PUT 分支直接 model.update，然后记录日志，没有调用排课冲突校验、课程变更事件、扣课时/薪酬同步等业务服务。

反馈通用编辑允许改变 status，可能跳过正常发布路径中的校验和通知；改知识点又不一定同步已有知识卡。普通“字段更新成功”不能保证三个客户端的业务结果一致。

建议：这些字段改为只读；跳转“调整课次”“修正考勤”“修订反馈”等受控流程，复用对应业务服务。保留前后差异、原因和审计记录，而不是只保存底层字段。

### P1：永久清理将正常归档视为废弃

`src/app/api/admin/cleanup/route.ts:17–31` 以 status=ARCHIVED 查班级并硬删除相关考勤、成绩等；没有要求这些班级先被软删除。设置的 BackupTab 将此能力放在“永久清理”中。

有超级管理员及确认短语保护，这是正确的；但“正常历史班级”和“废弃数据”仍不是同一回事。管理员可能以为只是清理垃圾，实际删除需要保留的历史学情数据。多个对象分批事务也不代表整次清理原子完成。

建议：永久清理只处理已进回收站、超过保留期、经预览确认的数据；不得因离校/离职/归档就自动视为垃圾。执行前生成可恢复完整备份，按任务记录进度及失败对象。

### P1：两种“备份”不是同一能力，JSON不完整

- 设置备份 `src/app/api/settings/backup/create/route.ts:14–41` 导出部分业务JSON，考勤最多5000条、试卷最多1000条，未包含完整账号配置、课堂反馈、照片文件及所有关联表。不是完整系统恢复备份。
- 数据管理备份调用 backup-now.sh；恢复端使用pg_restore和受控备份目录，是另一套格式。
- `BackupTab.tsx:24–31` 没有检查HTTP成功与否，就把返回JSON下载并提示“备份文件已下载”。服务器返回错误JSON时也可能被当作成功备份。

建议：设置里的JSON改名“业务数据导出”，列明范围、截断与不能恢复的限制；真正可恢复的备份统一到维护中心，显示格式、范围、文件完整性和验证状态。数据库、上传文件与配置的备份范围分别说明。

### P1：覆盖恢复存在部分完成风险

`src/app/api/admin/data-admin/restore/route.ts:55–65` 用pg_restore --clean，没有 --single-transaction 或 --exit-on-error。恢复失败可能已覆盖部分对象。

96–107行恢复BOTH时先执行初中库，再检查高中dump与连接并恢复高中库；若后者失败，初中已变更。当前统一HTTP结果和最后的日志不能完整表达“一个库成功、一个库失败”。覆盖后写日志也不是恢复结果验证。

建议：先验证两库输入、数据库版本、迁移与文件完整性，再做恢复前备份和维护隔离；采用独立任务跟踪各库结果，优先恢复到临时库验证后切换，不直接依赖一个网页请求执行覆盖恢复。

### P2：角色权限与通知开关未找到业务消费者

角色开关 teacherViewFee、teacherViewOthers 写入RoleConfig；通知开关 paperPush、absenceAlert、performancePush、lowHoursWarn 写入NotifyConfig。搜索设置目录之外的src与scripts，未找到这些字段或模型的读取路径。

依据：`src/app/api/settings/roles/route.ts:28`、`notify/route.ts:28` 只存配置；`RolesTab.tsx:35`、`NotifyTab.tsx:32` 对用户宣称实际权限与推送行为。

这不是已经证实的教师越权；相反，当前已有权限守卫继续执行固定规则。问题是管理员改变开关后，不能据此相信对应权限或提醒行为已改变。

建议：每个设置建立“配置项→消费者→验收用例”；没有接入的开关隐藏或标明未启用。权限必须在服务端生效，不只隐藏按钮；通知区分站内提醒与外部推送，不笼统写“推送成功”。

### P2：多处失败却显示成功，断网可能一直加载

- `SubjectsTab.tsx:50–62`、`RoomsTab.tsx:18–30`、`FeeTypesTab.tsx:18–26` 保存没有检查res.ok，错误响应仍显示成功并关闭表单。
- `RolesTab.tsx:13–16` 类似；开关数据可能根本没保存。
- `OrgInfoTab.tsx:22–35` 保存没有try/finally，网络异常后saving可能不复位。
- LogsTab等SWR fetcher只解析JSON，错误可能变成空列表，而不是“读取失败”。

建议：全部使用统一请求封装，错误落在具体字段或操作旁；保留草稿，失败不关闭弹窗；提交中禁重复点击并允许重试。禁止下载失败内容作为正常导出文件。

### P2：学科、机构配置与页面使用源分离

学科设置写Subject表；资料管理、教师上传、家长资料仍用 `src/data/subjects.ts` 的GRADE_SUBJECTS与SUBJECT_COLORS。在设置外未找到Subject表/学科接口消费者。

学科改名 `src/app/api/settings/subjects/[id]/route.ts:20` 只改Subject记录，课程等仍以学科名称字符串关联；删除又按原名称查依赖。因此不是单纯改个标签就能安全联动。删除接口已有依赖检查，应保留。

机构名称、英文名、logoUrl在设置外未找到应用路径，当前保存配置不等于修改登录页或品牌导航。

建议：区分“机构可配置学科目录”和“教材年级学科范围”，不要把教材规则变成任意可编辑列表。明确学科配置作用范围，采用稳定ID/重命名迁移。机构资料若仅用于档案就明说；若用于官网/三端品牌则增加统一读取和缓存刷新。

### P2：账号管理三套入口展示口径不一致

账号管理使用 `/api/settings/accounts`，能处理管理员、教师、家长；教师账号和家长账号又用独立列表接口。统一账号接口已有密码脱敏、审计和最后管理员保护，不应重做或删掉。

家长账号普通列表 `parent-accounts/route.ts:46` 只走User.students关系，查询的是parentId关联；同文件的绑定选择分支却同时查parentId/parentUserId。按parentUserId绑定的孩子可能在普通列表遗漏，历史身份也没有统一归并。

教师账号接口不返回teacherId/关联档案状态，界面还将邮箱写成“拼音@tea.com”；管理员难以发现自定义邮箱教师的未绑定档案。

建议：一个“账号与绑定”中心，按角色筛选；展示账号状态、档案状态、关联身份、登录状态与异常。不要把停用账号、离职教师、离校学生混为同一个状态。旧入口保留重定向。

### P2：统计、健康结果和刷新不是同一口径

- `overview/route.ts:34` “本月课次”只有本月起点，没有下月上限，未来月份已排课程也会计入。
- 部分列表/概览用业务status过滤，业务页面用status+deletedAt，容易同一条记录在不同模块算进不同结果。
- 健康查询多数LIMIT50，count由结果数组长度产生，是样本数而非完整异常总数。
- 健康raw SQL未显式按division过滤；单库多学部部署需要核查范围。双库部署中该问题不等价于跨库泄漏。
- 列表编辑/批量操作只mutate当前列表；已加载的概览和健康结果不会一起刷新。

建议：统一范围对象（学部、批次、时间、软删除状态）；计数和样本分开查询；修改后刷新相关概览/健康/业务缓存，健康发现直接链接到对应修正流程。

### P3：切换设置会卸载表单，手机13个页签难发现

SettingsContent用条件渲染切换13个组件，未保存的表单随切换丢失。手机版横向最小宽度tabs.length*72，多个类别长期藏在右侧；无效tab参数没有匹配内容，可能空白。

建议：分组目录或移动选择器；保留草稿/离开提醒；无效tab回退默认；用中文业务名称替代数据库字段。此项是代码推断，未在浏览器复现。

## 四、建议的最终结构

系统设置保留四组：基础设置（机构、目录、教室、费用类型）；账号与安全（账号、绑定、真实权限）；消息与权益（消息规则、家长权益文案、教师福利文案）；审计（日志）。

数据管理保留三组：健康诊断（默认异常待办）；受控修正（对账、身份、关系修正，链接业务表单）；维护中心（备份、验证、恢复、回收站保留期及高级清理）。底层表浏览只读，放高级工具。

所有报表与业务数据导出统一到报表/导出中心。旧链接兼容跳转，不删除已有照片、历史反馈、档案或导出能力。

## 五、建议实施与验收

1. 先修删除恢复和直接修改业务状态的绕路，暂不进行真实永久清理。
2. 修统一请求反馈、typed表单及范围/刷新；保存失败保留输入。
3. 把JSON导出与可恢复备份分开，覆盖恢复改成可跟踪任务。
4. 合并账号入口，统一parentId/parentUserId及identityId口径。
5. 为每个设置登记消费者；角色/通知没接通前明确禁用或未启用。
6. 最后调整目录、移动导航和草稿连续性。

必须补的测试：单条/批量删除结果一致；恢复后家长可见且关联完整；取消课程触发通知；考勤修正同时对账；numeric/boolean/array字段正确校验；500响应不能提示成功；500响应不能下载成备份；历史账号绑定两种字段一致；每个权限/通知开关对真实接口生效；备份恢复覆盖照片与反馈；双库恢复失败明确部分状态；正常归档不会进入永久垃圾清理；设置切换保留草稿。

本报告没有宣称上述问题均已修好。已有分域测试、身份人工核对、危险操作确认、密码脱敏与审计、回收站服务应复用，而不是另造一套后台。

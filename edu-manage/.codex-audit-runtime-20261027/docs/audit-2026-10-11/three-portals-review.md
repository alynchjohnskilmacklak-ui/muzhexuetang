# 三端功能、数据链路与界面整理审查

审查日期：2026-10-11。性质：只读审查，未修改业务代码、数据库或生产服务器。

## 结论

现在最需要的不是再增加入口，而是统一“孩子身份、数据范围、操作状态”。页面已经有不少可用功能，但历史批次与身份的衔接、独立页面的数据口径，以及看似完成的模拟入口仍会降低可信度。

优先处理：历史孩子重复、首页跨期统计遗漏、成长档案 Hook 顺序、请假通知可靠性、个性化课程详情口径。之后再整理入口和视觉层级。

## 审查范围与证据边界

- 浏览器实查：当前已登录家长账号的手机宽度首页、VIP、学习资料、题库入口、课堂反馈列表及导航菜单。截图均为本轮实际页面，不是设计稿。
- 代码核查：家长身份选择与首页聚合、VIP/个性化课程详情、缴费、成长档案与导出、请假链路、教师课表包装页、教师反馈请求封装、管理端导航与沟通中心。
- 全量自动检查：TypeScript 类型检查通过；Vitest 125 个文件、548 项测试通过。全仓 ESLint：176 个错误、4264 个警告；限定 `src`：10 个错误、95 个警告。大量全仓警告来自临时脚本等，不能把总数直接当作业务故障数。
- 未做：切换当前家长会话去逐项操作管理端/教师端；收费、删除、考勤、反馈发布等写入测试；生产环境巡检；图片网络性能基准；全部屏幕尺寸与真机测试。因此本报告不是“所有功能均已验收通过”。
- 没有访问统计，不能仅凭代码断言某功能“没人用”。下文区分故障、可合并结构与低优先级入口。

## 一、优先修复的逻辑问题

### 1. 高：历史批次仍显示为多个孩子（实图确认）

VIP 中显示“马子墨、马紫晨、马紫晨、马子墨”；首页也显示周末班和暑假班的独立记录。浏览器 DOM 核对确认这些按钮属于同一个列表，不是两套控件叠加。

代码依据：`src/lib/parent-student-selection.ts:19` 仅按显式 `identityId` 合并；`src/lib/parent-children.ts:20` 使用该规则。安全地避免同名误合并是正确的，但旧记录没有完成身份关联时，重复仍会出现。未直接查询这四条记录的数据库身份字段，具体缺失或分裂情况需只读审计确认。

处理：管理端列出同一家长下的疑似跨期记录，人工确认后建立稳定身份关联；界面一个孩子一个入口，批次作为筛选而非另一个孩子。不能恢复按姓名自动合并，更不能删除旧考勤、反馈和账单。

验收：这两个孩子各一个入口；旧批次记录仍能查；同名但不同身份不合并；返回、刷新、切换页面都保持所选孩子。

### 2. 高：首页合并身份后仍会丢失历史记录范围（代码确认）

`src/lib/parent-dashboard.ts:83` 使用 `selectLatestParentStudents` 只保留代表记录，86 行只取这些 ID。反馈查询与 363–389 行统计按代表 ID 匹配，不保留 `recordIds`。即使修好身份关联，旧 ID 上的反馈、徽章、作答等仍可能没有归到首页的这个孩子。

处理：首页也使用统一孩子查询，保留授权范围内的全部 `recordIds`；展示按身份聚合，具体操作按真实课次/报名记录落库。明确统计是本月、当前批次还是全部历史，不混口径。

验收：同一孩子两期记录能按指定时间范围正确聚合；其他孩子的数据不混入；首页最新关注与反馈列表一致。

### 3. 高：家长成长档案有条件 Hook（静态确认，未复现崩溃）

`src/app/parent/archive/client.tsx:392` 无孩子时提前返回，421 行之后仍调用 `useMemo`。绑定列表从空变非空、或反向变化并复用组件时可能改变 Hook 数量。ESLint 也报告 rules-of-hooks 错误。

处理：所有 Hook 放在提前返回之前；覆盖无孩子、有孩子及 props 更新的组件测试。346 行的函数声明顺序告警需另查依赖与闭包，不应等同于已证实立即崩溃。

### 4. 高：请假通知收件人与落库可靠性不足（代码确认）

`src/app/api/parent/leave/route.ts:94` 根据主负责老师姓名拼出 `@tea.com` 邮箱查账号，而不是稳定教师账号关联；不一定通知该课次实际授课教师。非标准邮箱、改名或主负责老师不同于任课老师，会漏通知或通知错对象。

57 行先创建请假记录，再顺序创建管理员通知、教师通知和日志，未见同一事务或可靠事件队列。后续步骤失败时，业务已成功而请求可能报错；重试有重复申请风险。

处理：课次任课教师优先，稳定账号关联；主负责老师按业务规则抄送。请求幂等，核心记录与通知事件原子保存，异步投递可重试。页面区分“申请已保存、通知待重试”和“保存失败”。

### 5. 中：VIP 与个性化课程详情仍是两套查询口径（代码确认）

`src/app/parent/intensive/page.tsx:27` 查询原始学生，没有统一身份聚合；39、63、68、91、99 行仅匹配单个记录 ID。99 行课堂反馈只限制 PUBLISHED，未限制 `deletedAt`。这些条件与 VIP 新链路不一致，详情可能缺历史数据，软删除反馈也可能再次出现。

处理：共用授权、身份及历史课次服务，保留详情路由和有用内容；反馈统一发布与软删除过滤；无效孩子明确提示，不静默选择另一孩子。

### 6. 中：缴费重复筛选，且存在未完成的支付入口（代码确认）

`src/app/parent/fees/client.tsx:33` 有 ChildSwitcher；43 行又有按姓名筛选的下拉框。25 行按姓名匹配，不能可靠区分同名学员。`fees/page.tsx:18` 按单记录 ID 查询，不解析跨期别名，也未读取统一孩子偏好。

61、76 行显示“立即缴费”，28 行实际只弹出模拟支付提示，没有支付闭环。

处理：保留一个按稳定身份的孩子筛选；金额卡片与列表使用相同筛选口径。支付未接入时改为明确的“查看缴费方式/联系机构”，或禁用并说明，不能伪装成实际付款。保留账单与已缴记录功能。

### 7. 中：沟通中心标签与内容不一致，切 Tab 可能丢草稿（代码确认）

`src/app/(main)/communication-center/page.tsx:28` 名为“家校公告”，实际加载 `communications/page.tsx:93` 的学习档案/在校表现家长评论管理，不是公告发布。24 行销毁非活动 Tab，回复或通知草稿需要确认是否有持久保存，否则切换即丢。

处理：改为“课堂/档案评论”；私信、评论、通知共用待办汇总，但保留来源和各自权限。抽取不带 PageLayout 的内容组件，避免容器嵌套。草稿保留或离开提醒。`communications/page.tsx:73` 回复 fetch 无网络异常捕获，应加明确失败提示并保留输入。

### 8. 中：PDF 导出按长截图机械分页，有内容切断风险（代码确认，未导出验收）

`src/app/parent/archive/client.tsx:375–385` 将完整报告生成一个 canvas，再按 A4 页高切割。正文、照片、公式可能跨页被截断；长报告在手机上还有内存风险。useCORS 不能保证所有照片成功出现在导出中。

处理：统一报告数据模型、分块分页，保留个人信息、课堂反馈、知识点、练习、课堂照片。图片加载完成或明确标记缺图后才导出；大报告采用分页渲染/服务端渲染。不要把完整学情报告简化成几张统计卡。

### 9. 中：部分壳层请求仍把失败 JSON 当普通数据（代码确认）

`src/components/Layout/ParentLayout.tsx:47` fetcher 未检查 HTTP 状态。教师反馈页已经使用 `fetchJson`，不应重复重做已修好的部分。

处理：剩余请求统一到相同封装；401、403、500、离线与空数据分开显示。请求失败时不把未读数当作零，不触发错误的“没有记录”提示。

### 10. 低：带查询参数的导航无法正确高亮（代码确认）

`ParentLayout.tsx:53` 与 MobileLayout 的活跃项计算基于 pathname，导航中却有 `/parent/archive?tab=hours`。pathname 不含查询参数，课时入口的高亮可能落在成长档案上。

处理：按 pathname + 指定 tab 查询参数判定，不把所有查询参数都加入匹配；保留同一档案中的不同视图。

## 二、界面与手机端

本轮截图保存在本目录。没有把 Next 本地开发浮层的“N / Issues”当作生产缺陷。

| 课堂反馈 | 卡片结构已较清晰，保留学科、老师、日期和摘要；历史记录较多且未读91 | 优先最近、未读与需练习筛选；按日期/课程分组；详情保留完整正文和课堂照片，不将内容藏得过深 |

主题代码仍存在大量字面颜色，例如 VIP 的绿色/金色和学习资料的独立背景色。检测器将其标为设计系统之外的 advisory，不能据此认定所有定制颜色错误。正确方向是把已经认可的等级配色补成语义 token：页面背景、卡片背景、正文、次级文字、边框、选中态、错误态分别定义，保留高级主题，避免再次逐页补字色。

移动端44px为项目易用性目标，不把35.5px自动称为WCAG违规；还需结合间距和可点击区域判断。颜色对比度、键盘导航、屏幕阅读器、照片题横屏及其它等级主题尚未完成专项验收。

## 三、重复功能怎么整理

| 功能组 | 保留什么 | 合并/整理什么 |
| --- | --- | --- |
| 孩子选择 | 多孩子、历史批次、全部孩子视图 | 统一身份服务和选择状态；页面只保留一个选择器；全部视图仅在支持跨孩子聚合的页面出现 |
| VIP/课表/个性化详情 | 预约、课次、反馈、审核进度和详情链接 | 共用课程参与关系与历史查询，不再分别定义权限与软删除口径 |
| 成长档案/学习分析/周报/报告 | 各场景下必要的入口、完整报告和照片 | 同一报告数据模型；档案是长期查看，周报是摘要，导出是完整快照；不是粗暴删除分析能力 |
| 学习资料的题库分类/在线练习 | 文件题库上传、在线作答、错题回看 | 文件与在线题组用同一目录入口区分类型；题库分类链接到练习，避免两处各维护一套章节 |
| 管理端学员管理/学情资料检查 | 前者档案与报名，后者查缺补漏 | 区分任务；资料检查直接深链到学员工作台，不复制完整编辑、导出功能 |
| 管理端私信/课堂评论/通知 | 私信沟通、对象内评论、通知发送各自语义 | 统一待办/未读汇总和处理状态，按来源区分；不能把不同权限对象直接揉成同一条记录 |
| 教师两种课表入口 | 兼容旧链接，课次详情 | `teacher/teaching-schedule/page.tsx:17` 单Tab包装可简化；共享Schedule内容组件而不是动态导入整个page |
| 教师反馈旧路由 | 旧链接跳转能力 | `teacher/classroom-feedback/page.tsx` 已是兼容跳转，不是重复功能，不需删除 |
| 管理端导航 | 现有分类与入口 | 已共用admin-nav定义，无需再重复实施“统一导航” |

### 低价值入口：调整展示，不直接删功能

- 未报名晚托的家长：晚托作业不必长期占底部主导航，放更多/服务介绍；报名后恢复核心入口。
- 非升学阶段孩子：高中学校库/志愿工具可放服务区，接近适用年级再提高优先级。保留家长主动访问途径。
- 未报名VIP：短介绍足够，已报名时优先课次和反馈。
- 天气、诗句、等级装饰：保留情绪价值，但不能挤掉真实学习信息。
- 模拟支付：明确替代为实际可用操作，不新增装饰性“成功”。

这些是场景相关性建议，不是根据真实使用率认定“没用”。建议先记录各角色入口访问、任务完成和失败次数，再判断是否下线。

## 四、三端应该侧重什么

- 管理：当前批次异常待办优先；空名单课次、未完成考勤、未发布反馈、通知失败可追踪；从异常到处理页保持同一个课次/孩子范围。
- 教师：今日课次→实际上课学生→考勤→逐学生反馈→发布结果；AI生成和照片上传保留，草稿与失败对象可重试，不额外重复填表。
- 家长：当前孩子→最新真实反馈→本节练习→错题与进步→完整报告；长期资料和服务作为补充，不能用推广或等级装饰替代专属内容。

## 五、验证与实施顺序

1. 只读审计历史身份及授权关系，人工确认疑似跨期记录；统一孩子范围并修首页统计遗漏。
2. 修条件Hook、请假稳定账号关联/幂等/通知事件、个性化详情软删除与参与关系。
3. 清理缴费重复筛选与模拟按钮；修沟通中心标签和草稿；补剩余失败反馈。
4. 共用报告数据和分页导出；保留完整正文、个人信息和课堂照片并实际验收PDF。
5. 最后精简首屏、主题token、触控区、按报名状态显示服务入口；保持原有可用业务功能。

必须新增的回归用例：同一家长两孩子各两批次；同名不同身份；首页→反馈→练习→缴费保持孩子；旧记录ID深链；未发布/已删除反馈不显示；请假保存后通知失败重试；非标准邮箱教师收通知；切Tab草稿不丢；空绑定列表变有孩子；含长文、公式、照片的跨页报告；接口401/403/500及离线。

## 六、测试结果如何理解

548项测试通过与类型检查通过是基础，不证明当前历史数据、实际通知投递和全部浏览器流程正确。ESLint的10项src错误中，成长档案Hook最应优先处理；另外包括管理/教师首页render读取ref、显式any及WeeklyReport普通a标签导航。应逐项解释和修复，不能通过批量关闭规则掩盖问题。

本轮依据实际截图、Impeccable静态提示与UI UX移动交互指导区分“已确认问题”和“待验证风险”。未做完整WCAG认证或全端性能评测，故不提供看似精确的全系统评分。

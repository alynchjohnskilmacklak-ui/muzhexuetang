# 牧哲学堂·教育系统能力差距与开源移植调研报告（2026-11-05）

## 一、一页纸摘要

- 系统现状：牧哲学堂是已上线的单校区 K12 教培三端运营平台（管理端、教师端、家长端），Next.js 16 App Router + React 19 + TypeScript + Prisma 5 + PostgreSQL + Ant Design 5 + ECharts + Redis + 阿里云 OSS + 企业微信/WxPusher；89 个 Prisma model、124 个 page.tsx、296 个 api/route.ts，服务几十到一两百名学员。
- 核心判断：本系统不缺功能清单，缺的是"把已有数据用起来"和"把已有流程闭环"。89 张表、296 个接口已覆盖教培经营的绝大部分对象，本次核查发现的 21 条问题中绝大多数是质量缺口（骨架已在、差最后一公里），真正的功能缺口集中在作业闭环、招生 CRM、在线收款、小程序等少数环节。
- 外部对标结论：22 个优秀教育产品、60 条能力矩阵比对后，可借鉴的是作业闭环、成绩册、家校通知、成长档案、招生漏斗与经营看板；LMS 与公立校 SIS 的课标、学分、考务、学籍、多语言等能力与本业务模型不匹配，不应照搬。三类产品可借鉴点不同：LMS 学作业与成绩册、家校系学家长感知、教培 SaaS 学经营链路。
- 开源结论：核实 65 个仓库后，可直接取用的仅 10 项组件/库；Moodle、Frappe LMS、EduSoho、Canvas、Open edX、Chamilo 六套整套系统替换均不做；教育垂直开源项目多为整套系统，受许可证、技术栈、数据模型三道门槛阻挡，搬不动；课堂实时互动、中文发音评测、题库组卷算法、独立作品集组件在开源侧没有成熟宽松实现，只能自研。
- 优先级：P0 六条先补最后一公里（0–6 周）；P1 八条补真正的功能缺口（6 周–4 个月）；P2 七条可做不着急（4–12 个月）；D 八条明确不补，附重新评估触发条件。
- 如果只能做三件事：A1 通知预警接线、A2 普通课程作业闭环、A3 成绩册前端。这三件直接改变家长在微信端看到的关键事件感知，是家校信任与续费体验的最短路径。
- 工作量口径：1 人全职、熟悉现有代码库，按人日区间估算；未含产品调研、视觉走查与上线后回归缓冲。
- 风险提示：本报告只做能力与工程判断，许可证影响均为事实陈述，不构成法律意见；对外商用前由法务逐条复核 LICENSE 原文。

## 二、方法与证据口径

本报告只做总装与写作，不重复核查工作。证据来自四份已核实材料：教学链路代码核查（01，12 项证据 + 8 条新发现）、运营家校链路代码核查（02，14 项证据 + 8 条新发现）、外部产品能力对标（03，22 个产品、60 条能力矩阵、46 个实测链接）、开源可移植清单（04，65 个仓库，API 与 LICENSE 原文核实，取数日 2026-11-05）。

结论分三类标注：功能缺口指业务对象或流程整体不存在；质量缺口指骨架已在、差最后一公里（有表无界面、有接口无消费方、有配置无执行、有统计无分析）；规模不匹配指能力存在但对当前机构规模属于过度设计，计入不补清单。凡 01/02 判定为"有但半成品"的条目，本报告一律写成质量缺口，不写成缺失。

每条缺口均可回溯到 01/02 的具体序号，报告中以"（见 01-第 3 项）"形式标注，并附关键文件路径；优先级档位沿用委托方已定口径，未作调整。核查中若出现材料之间不一致，以证据文件为准并在正文标注。本次未发现与口径冲突的实质性矛盾。

三类产品的设计假设不同，不能互相套用。国际 LMS 强在课程结构、作业测评、成绩册与学习过程记录，角色以教师—学生为主，基本不处理招生、收费、课消、课酬等经营问题；K12 家校系依附公立校建制，强在课堂之外的家长感知与作品档案，不承担机构经营转化；中国教培 SaaS 才覆盖排课、考勤课消、收费退费续费、课酬与经营报表。因此"没有复用"要分开判断：作业、成绩册向 LMS 学，家长通知、作品档案向家校系学，招生漏斗、课消课酬、经营看板向教培 SaaS 学。

> 反向对照：以下几块本系统已经自建，A/B 类产品基本不覆盖，属于本平台相对通用 LMS 与家校工具的经营侧存量优势：晚托作业班全链路（报名额度、场次登记、作业前后照片、闭馆日安排）；就餐订餐（菜单、模板、订餐报表）；中考志愿填报指南（志愿步骤、配额/分配生数据、咨询记录）；教师薪资结算与课时流水课消；家长已读回执与反馈奖励台账。这些能力是教培经营场景下的私有规则，外部系统不包含；对标是补短板，不是把已有存量推倒重做。

### 4.3 整套替换：明确不做

Moodle、Frappe LMS、EduSoho、Canvas LMS、Open edX、Chamilo 六套系统均核实过，结论一致：不做替换。它们以课程内容承载与在线学习交付为中心，而本平台核心价值在机构经营链路（排课—考勤—课消—薪资—反馈—家校推送）与三端私有业务逻辑，替换等于把已上线的私有逻辑再实现一遍。

代价按六个统一维度衡量：一是数据模型冲突，LMS 围绕课程—章节—作业—测验—成绩册—用户建模，课消口径、薪资结算、就餐订餐、晚托作业班、中考志愿、成长徽章、家长回执等无对应表结构，迁移需反向 ETL 与双写过渡；二是三端 UI 重建，现有 React 19 + AntD 5 组件与样式无法复用到 PHP/Ruby/Python/Vue 模板；三是企微/微信家校链路需重新对接绑定、模板消息与回调；四是私有业务逻辑（四态考勤扣课、课时流水、薪资口径、徽章权益、晚托完成度、AI 反馈策略）任何 LMS 都不包含，需重写并回归；五是运维栈另建一套运行时、数据库、队列与缓存；六是许可证与合规，GPL/AGPL 对二次开发、网络服务与镜像分发有 copyleft 约束（事实陈述，非法律意见），未成年人数据存储与日志需重新合规评估。

逐项事实卡：Moodle（GPL-3.0，PHP，课程活动/测验/成绩册成熟但经营模块空白）；Frappe LMS（AGPL-3.0，Python Frappe + TS 前端，轻量定位与当前规模不匹配，网络条款对经营性 SaaS 是实质约束）；EduSoho（自定义 EULA，PHP，商用须购授权、禁止派生版本再分发、须保留厂商页脚标识，协议风险最高）；Canvas LMS（AGPL-3.0，Ruby on Rails，模型围绕学校场景）；Open edX（AGPL-3.0，Python/Django 重型平台，面向长周期在线课程）；Chamilo（GPL-3.0，PHP，功能以课程/作业/成绩册为主，经营模块缺失）。

### 4.4 教育垂直开源为什么搬不动

点名核实的中文/教育垂直候选共 7 项，结论均为不建议直接取用：PlayEdu（Apache-2.0 主体 + README 署名/修改备注附加条款，SpringBoot3/Java17/MySQL/React18 整套培训系统）；学之思 xzs-mysql/uexam（AGPL-3.0，Java Spring Boot + Vue 整套考试系统，网络 copyleft 是主要否决项）；XIAOJU-SURVEY（Apache-2.0，NestJS + MongoDB + Vue3 整套问卷平台）；Timefold Solver（Apache-2.0 CE，Enterprise Edition 商业闭源，Java/Kotlin 求解库，仅作排课备选对比）；酷瓜云课堂（GPL-2.0，PHP Phalcon C 扩展框架 + layui 整套网校）；智教云（MIT 但为个人项目、star 4、Java 8/Spring Boot 2.2 老旧，不可作生产基线）；微厦 LearningSystem（自定义 WPL 2.0，禁止商业用途，C# + PostgreSQL + Vue）。

搬不动的原因是三道门槛叠加：许可证上，AGPL/GPL/自定义非商业协议对经营性对外服务平台构成约束；技术栈上，Java/PHP/Python/C# 与现有 Node/TS/Prisma/PG 体系割裂，需新增运行时与独立数据库；数据模型上，这些项目多为整套系统而非可嵌入模块，自带用户、部门、题库、课程模型，与主库不互通，旁挂还要做鉴权打通与数据对账。此外厂商开源与商业版双线维护，开源版功能边界随商业策略调整。

### 4.5 检索缺口：这四块只能自研

04 核实中如实记录四块方向，开源世界没有成熟、活跃、许可宽松、可直接嵌入 React 三端的实现：课堂实时互动（随机点名/抢答/投票/答题器/计时），命中多为课程作业级 Demo；中文发音评测/朗读打分，仅有 ASR 转写引擎，音素对齐与评分层需自研；独立题库组卷算法与错题本组件，实现多内嵌在整套考试系统内，无可单独抽取的宽松许可算法库；独立作品集组件，未找到成熟开源模块。这也是 Part A 中 B1、B5 工作量偏大的原因：对应能力在开源侧没有现成轮子，增量集中在现有链路上自研。

### 5.2 三段判断

第一，一句话结论：这个系统不缺功能清单，缺的是把已有数据用起来和把已有流程闭环。89 个 model、296 个 API 已经把教培经营的对象建得差不多了，当前最大的损耗是"数据进去了没被消费、流程走到一半断在配置壳和标志位上"。先把 P0 六条接线做完，系统呈现给家长和老板的面貌会明显改善，再谈新增模块。

第二，如果只能做三件事：A1 通知预警接线、A2 普通课程作业闭环、A3 成绩册前端。理由是这三件直接作用于家长感知：家长在校外最在意的是孩子的课有没有被盯到、作业有没有被改、成绩有没有被看见。A1 让旷课、低课时、成绩、欠费这些关键事件真正推到家长微信端；A2 把课后作业从微信群收作业变成系统内可追溯的提交—批改—回批；A3 让已录入的成绩变成可查看、可对比、可导出的成绩单。三者叠加，家校信任与续费沟通的素材才真正成立；其余能力要么是后台效率问题，要么规模未到。

第三，什么时候重新评估不补清单：D1 多校区在第二校区开张、需要跨校区隔离与汇总时评估；D2 直播录播在业务转线上课或双师场景出现时评估；D4 自动排课在班级数排到人工冲突校验吃力、教师教室资源紧张时评估；D7 音视频作品集在艺术类（朗读、表演、乐器）课程上线时评估；D6 行为分析在需要做产品迭代决策或合规评估通过后评估；D5 独立 BI 在 ECharts 报表无法支撑分析维度时评估；D3、D8 属业务模型不匹配，除非机构转型为学校、成人培训或双语场景，否则不重新评估。学员规模越过 300 人是一条通用观察线：届时人工判断开始失效，再回头看 C1 分层推荐、B6 流失评分与 D1 租户模型的优先级。
